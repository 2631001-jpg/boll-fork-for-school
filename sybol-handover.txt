============================================================

- 주로 휴대폰에서 GitHub 웹사이트를 통해 HTML을 수정함. 로컬 개발환경을 전제로 한 안내는 피하고, 모바일 기준으로 안내할 것.
- 일반론보다 현재 프로젝트의 실제 코드와 오류에 맞춘 수정 원함.
- 수정할 때 파일 이름과 어디에 넣는지 명확히 알려줄 것. 파일 버전 번호를 붙여 구분하기를 원함.

- 전체 코드가 필요하다고 요청한 경우 부분 코드만 던지지 말고 완성된 파일을 제공할 것. 파일 생성이 실제로 끝났는지 확인하지 않고 완료됐다고 말하지 말 것.
- GitHub Pages에서 새 HTML 파일을 만들기만 해서는 메인 URL이 바뀌지 않는다. 메인 페이지 반영은 저장소에서 실제로 사용하는 index.html을 업데이트해야 함.
- 파일 경로는 실제로 존재하는지 확인한 후 링크를 제공할 것.

3. 핵심 기능 요구사항 및 변경 이력
============================================================
초기 커뮤니티 기능 요청:
- 다크 모드
- 자유 게시판
- 게시글 작성/수정/삭제
- 댓글 및 대댓글
- 추천/좋아요 및 인기 정렬
- 검색
- 프로필/닉네임
- 이미지 첨부
- 관리자 신고함
- Supabase를 이용한 실제 다중 사용자 DB/인증

이후 요청 및 수정:
- 게시글 클릭 시 해당 게시글 하나만 상세 화면으로 열리도록.
- 신고함에서 신고된 게시글 내용을 직접 확인.
- 신고 처리 상태 중 기각한 신고는 신고함에서 사라져야 함.
- 기존 “검토완료” 버튼을 게시글 삭제 기능으로 바꾸고 싶다고 요청한 이력이 있음. 실제 최신 동작은 코드를 확인해야 함.
- 개발자만 공지를 작성할 수 있게 요청했으나 이후 developer 역할 자체를 사용하지 않는다고 정리함.
- 관리자가 공지를 고정하면 사이트 상단, 기존 검색 위치에 고정 표시되게 요청함.
- 검색은 페이지 아래로 내리고 게시물 10개마다 다음 페이지로 이동하도록 요청함.
- 메뉴는 화면 아래쪽의 고정 메뉴가 아니라 페이지 흐름 안에서 움직이지 않는 고정 메뉴처럼 만들기를 요청했으며 메뉴 항목은 게시판, 마이페이지, 나의 채팅방, 친구.
- 마이페이지와 내 프로필이 같으므로 하나를 제거하고 친구 관리 버튼으로 바꾸기.
- 친구 검색/친구 추가, 보낸 친구 요청 목록.
- 링크는 실제로 눌릴 수 있어야 함.
- 단체 채팅방 기능: 개발자/관리자가 생성, 초대받은 사람만 입장. 이후 화면은 채팅창과 초대 화면을 분리해 달라고 요청함.
- 채팅 화면에는 메시지와 입력창, 새로고침; 별도 회원 초대 화면에는 닉네임 입력/초대 버튼; 화면 전환 버튼을 제공.
- 채팅방 생성에서 RLS 오류가 반복됨. RPC `create_chat_room(p_name text)`로 직접 INSERT를 우회하지 않고 서버 측 함수에서 권한을 확인하는 방향을 시도함. DB 함수/RLS와 프런트엔드 역할 검사가 서로 맞는지 반드시 함께 확인해야 함.
- Supabase 저장 용량/RAM 사용량 걱정을 물어봄.

4. Supabase 오류 및 과거 디버깅 기록
============================================================
반복적으로 마주친 오류:
- `permission denied for table profiles`
- `permission denied for table likes`
- `permission denied for table comments`
- `permission denied for table reports`
- `new row for relation "posts" violates check constraint "posts_category_check"`
- `new row violates row-level security policy for table "chat_rooms"`
- `email rate limit exceeded`
- `Failed to fetch`

당시 사용자가 공유한 정보:
- profiles 정책:
  - `profile self update`, role authenticated, UPDATE, 조건 `(id = auth.uid())`
  - `profiles readable`, role public, SELECT, true
- profiles 권한 조회에서 anon/authenticated에 SELECT가 부여돼 있었음.
- posts 테이블 SELECT는 anon/authenticated에 부여돼 있었음.
- likes/comments/reports에서 permission denied를 겪은 뒤 권한/정책을 고쳐 “성공”, “됨”이라고 확인한 적이 있음.
- chat_rooms 관련 정책 중 하나:
  - `Admins and developers can create chat rooms`
  - roles `{authenticated}`
  - `WITH CHECK`: `created_by = auth.uid()` AND profiles 테이블에서 auth.uid()의 role이 `admin` 또는 `developer`인 경우.
  - 다른 중복 정책 `Only developers can create chat rooms`가 한때 존재했음.
- chat_rooms 스키마:
  - id uuid NOT NULL DEFAULT gen_random_uuid()
  - name text NOT NULL
  - created_by NOT NULL
  - is_archived boolean NOT NULL DEFAULT false
  - created_at timestamptz NOT NULL DEFAULT now()
- profiles 예전 조회에서 admin 계정:
  - 닉네임 `sibol.`
  - role `admin`
  - 당시 표시된 ID는 `9ffc7b71-4d4e-4368-a7af-ea3243e22169`
  - 이는 과거 공유된 DB 결과이며 현재 상태라고 보장할 수 없음.
- 다른 프로필의 role은 `user`로 표시됨.
- 사용자가 Supabase SQL에서 역할 변경 시 다음 오류를 공유함:
  `ERROR: P0001: Changing role requires administrator privileges`
  `CONTEXT: PL/pgSQL function public.prevent_role_escalation() line 5 at RAISE`
- 해당 오류는 `prevent_role_escalation()` 트리거가 역할 변경을 막았음을 시사함. 보안 트리거를 삭제하거나 우회하지 말 것.
- 사용자 요청에 따라 co-operator 도입은 취소되었고 admin 체계를 그대로 유지하기로 함. Supabase role/RLS/role-protection function은 더 이상 임의로 바꾸지 말 것.
- 사용자는 developer 역할/계정이 애초에 없고 자신은 admin이라고 설명함. 코드에 developer 참조가 남아 있으면 admin 기준으로 정리하자는 데 동의했음.
- 중요한 점: 프런트엔드 코드에서 `developer` 문자열을 지워도 Supabase의 RLS/RPC 함수가 developer를 요구하면 기능이 실패할 수 있다. DB 정책/함수는 별도로 검사해야 하며 사용자의 명시 없이 변경하지 말 것.

5. 친구 및 채팅 관련 현재 알려진 코드 패턴
============================================================
- Supabase JS v2 CDN 사용.
- 친구/채팅 관련 테이블 이름:
  - `chat_rooms`
  - `chat_room_members`
  - `chat_messages`
  - `profiles`
- 채팅방 목록 로딩:
  1. chat_room_members에서 현재 user.id의 room_id 목록을 가져옴.
  2. chat_rooms에서 해당 ID들 중 is_archived=false인 방을 가져옴.
- 채팅 메시지 쿼리:
  `db.from("chat_messages").select("id,room_id,user_id,body,created_at,profiles!chat_messages_user_id_fkey(nickname)").eq("room_id", activeChatRoom.id).order("created_at",{ascending:true}).limit(200)`
- 채팅방 생성 RPC 호출:
  `db.rpc("create_chat_room",{p_name:name})`
- 초대:
  profiles에서 닉네임으로 회원 검색 후 `chat_room_members`에 `{room_id, user_id: target.id, invited_by: user.id}` INSERT.
- 기존 v12/v13 코드에 `["developer","admin"].includes(profile?.role)` 조건이 남아 있던 버전이 있었음. 나중에 admin-only 파일을 만들었다고 했으나 실제 모든 조건이 완벽하게 제거됐는지 재확인 필요.
- 사용자가 채팅창과 초대 화면을 분리해 달라고 요청했고 v13 파일을 제공한 적이 있음. 이 파일을 수정할 때 원본을 확인하고 기존 기능을 유지할 것.

- `index-v6.html`: 이후 수정 시 사용하려고 했던 버전 번호.
- `index-v11.html`: 채팅방 생성 오류를 해결하려고 기반으로 삼으려 했던 HTML.
- `index-v12.html`: RPC 방식 채팅방 생성 변경을 반영했다고 제공했던 파일. 그때도 완료/검증 여부에 혼선이 있었음.
- `index-v13.html`: 채팅창과 초대 화면 분리 작업을 위해 기반으로 사용된 파일.
- `index-v14-admin-only.html`: developer 검사 일부를 admin 기준으로 바꾸고, footer 저작권 표시를 추가했다고 제공한 파일.
- 대화 파일 검색 결과에는 `index (1).html`이 있었고, 크기 약 50,689 bytes, 수정일 2026-10-17. 이 파일의 HTML title에는 v12라고 적혀 있었음. 실제 최신 사용 파일과 동일하다고 단정하면 안 됨.
- 파일을 수정하기 전 반드시 실제 현재 파일을 읽고, 버전/기능/코드 검사를 할 것. 이전에 수정된 파일을 다시 찾을 수 없다면 사용자에게 재업로드 요청.

7. 권한 설계 결론
============================================================
사용자가 최종적으로 확정한 방향:
- co-operator 도입 취소.
- admin은 그대로 유지.
- 권한 체계 자체를 변경하지 않음.
- Supabase role/RLS/role-protection function을 임의로 변경하지 말 것.
- 사용자 자신은 admin이라고 밝힘.
- developer 역할 자체가 없다고 설명함. 프런트엔드에서 developer를 참조하는 코드만 admin 기준으로 정리하는 작업에 동의했음.
- 회원 정지/해제 기능을 추가해 달라고 했으나 이후 SQL에서 role 변경 오류가 발생함. 해당 기능의 SQL/프런트엔드가 안전하게 완료됐는지는 미확인. 정지 기능은 role 변경과 분리해 구현해야 함.
- 권한을 바꾸는 대신 기존 admin 권한으로 할 수 있는지 확인하고, 서버 측 정책은 명시적 승인 없이 변경하지 말 것.

8. 최근 사용자 요청
============================================================
사용자가 “너와 대화한 모든걸 넣은 txt 파일 만들어”라고 요청함.
이 파일은 현재 확인 가능한 프로젝트 맥락, 사용자 선호, 오류 기록, 요구사항, 권한 결론 및 파일 버전을 한곳에 모아 다음 세션에서 이어서 작업할 수 있도록 만든 인수인계 파일이다.
전체 과거 대화의 원문이 모두 포함된 것은 아니므로, 원문 전체가 필요하면 ChatGPT 데이터 내보내기 기능을 이용해야 할 수 있다.
